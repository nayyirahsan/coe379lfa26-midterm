\section{System Overview}
Atlas asks the model for one typed decision at a time. A trusted \texttt{LabRequest} supplies the authenticated user and any resolved project, resource and time interval. The system prompt distinguishes this envelope from user text, retrieved passages and tool observations. Retrieved instructions cannot override the request or bypass the action gate.

The decision union uses \texttt{kind} to distinguish a tool proposal, a clarification question and a final response. The loop requests decisions through \texttt{DecisionAdapter}, returns clarification without tool execution, and stops after at most ten decisions by default. Before dispatch, it checks the tool argument schema, request binding and reservation preconditions. Every allowed or denied tool proposal becomes a trace event, and its decision and observation are added to the next model context. A final-response check compares citation IDs and completed action names with successful observations before returning the result.

\section{Student Tests}
\texttt{tests/test\_student\_cases.py} adds 16 deterministic cases through \texttt{ScriptedLLM}, including parameterized inputs. Together with the 23 supplied cases, all 39 tests pass. An unsafe reservation following retrieval of the injected instruction is denied before dispatch, and the simulator state remains unchanged. Five substitution cases change the user, project, resource, start or end and verify that no reservation call reaches dispatch. Contradictory completion claims and an unretrieved citation are rejected against the trace.

Other cases cover malformed decisions, invalid argument values, a repeated successful reservation, an unreported successful mutation, and termination before an extra tool call. Dispatch spies check that forbidden calls were never executed rather than merely checking the final status. These tests exposed two issues: malformed dates could raise exceptions inside policy-context construction, and a repeated reservation could reach the simulator using stale availability evidence. Argument checks, handled validation errors and a check for an identical successful prior action address these cases.

\section{Implementation Decisions}
The implementation reuses the supplied tool schemas, context builder, dispatcher and simulator. Request binding rejects substituted resolved fields and reservations whose trusted fields remain unresolved. Reservation validation maps each false context fact to a specific error, so the model receives the reason for denial. Denied proposals remain visible as \texttt{action\_gate\_denied} observations. Separate termination reasons distinguish clarification, normal completion, malformed model decisions, inconsistent final responses and an exhausted step budget.

Final validation accepts only retrieved citation IDs and action names backed by successful mutating observations. A completed response needs a successful mutation and a completed action; a non-completed response cannot hide a successful mutation. These checks concern structured fields, not the full meaning of arbitrary prose. A successful policy search also does not prove relevance or policy completeness. Scripted tests establish behavior for selected proposals, not universal safety or live-model reliability. The step limit bounds iterations only if model and tool calls return. The separate \texttt{data\_flow\_diagram.md} follows the concrete successful reservation through these stages.
